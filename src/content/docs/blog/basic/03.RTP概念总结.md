RTP（Real-time Transport Protocol，实时传输协议）是一套面向实时媒体的传输协议，常用于语音、视频、会议、直播、VoIP、WebRTC 等场景。

一句话：RTP 通常跑在 UDP 上，它不保证可靠传输，而是给实时音视频数据增加媒体语义，让接收端知道包顺序、媒体时间、媒体源和负载类型。

RTP 的核心规范是 RFC 3550，常见音视频 profile 是 RFC 3551。

## 1. RTP 解决什么问题

实时音视频和文件传输的目标不同：

- 文件传输追求完整性，晚到的数据仍然有价值；
- 实时音视频追求时效性，过晚的数据通常没有播放价值；
- 网络会出现乱序、丢包、抖动、带宽变化；
- 接收端需要恢复媒体播放时间，而不能只看网络到达时间。

RTP 在 UDP 之上提供一层媒体语义：

```text
IP -> UDP -> RTP -> codec payload
```

RTP 主要提供：

- sequence number：检测丢包、乱序；
- timestamp：恢复媒体播放节奏；
- SSRC：区分不同媒体源；
- payload type：识别负载格式；
- RTCP：反馈质量信息，辅助音视频同步。

## 2. RTP 不解决什么问题

RTP 不是完整的音视频系统。它不负责：

- 建立连接、信令协商、编解码参数协商；
- NAT 穿透；
- 加密；
- 可靠重传；
- 拥塞控制；
- 业务层房间、用户、权限管理。

常见配套机制：

| 问题     | 常见机制                        |
| ------ | --------------------------- |
| 会话协商   | SIP、SDP、WebRTC offer/answer |
| NAT 穿透 | ICE、STUN、TURN               |
| 加密     | SRTP、DTLS-SRTP              |
| 质量反馈   | RTCP                        |
| 丢包恢复   | NACK、FEC、RTX、PLC            |

所以 RTP 更像实时媒体传输的基础骨架，而不是完整方案。

## 3. RTP 包头核心字段

RTP 固定头部最小 12 字节，面试重点看这些字段：

| 字段              | 含义                                 |
| --------------- | ---------------------------------- |
| V               | RTP 版本，当前为 2                       |
| M               | marker bit，含义由具体 payload format 定义 |
| PT              | payload type，负载类型                  |
| sequence number | 16 bit 序列号，每发一个 RTP 包加 1           |
| timestamp       | 媒体时间戳，不是 Unix 时间                   |
| SSRC            | 同步源标识，标识一条 RTP 媒体流                 |

### 3.1 sequence number

sequence number 用于包级别排序和丢包检测。它是 16 bit，会回绕。

例如收到：

```text
1000, 1001, 1002, 1004
```

接收端可以判断 `1003` 可能丢失。

sequence number 只能说明 RTP 包的发送顺序，不能表示播放时间。播放节奏主要依赖 timestamp。

### 3.2 timestamp

timestamp 表示媒体采样时间，单位由媒体时钟决定：

- 8 kHz 音频：1 秒 timestamp 增加 8000；
- 48 kHz 音频：1 秒 timestamp 增加 48000；
- 常见视频 RTP clock rate：90 kHz。

视频中，同一帧拆成多个 RTP 包时，这些包通常具有相同 timestamp：

```text
seq=10 ts=90000  frame A fragment 1
seq=11 ts=90000  frame A fragment 2
seq=12 ts=90000  frame A fragment 3
seq=13 ts=93000  frame B fragment 1
```

这里 sequence number 用来排序和组包，timestamp 用来表示帧时间。

### 3.3 payload type

payload type 表示 RTP payload 的格式。现代 RTP 大量使用动态 payload type，它的含义通常由 SDP 等协商结果决定。

例如：

```text
a=rtpmap:111 opus/48000/2
```

表示当前会话里 PT `111` 代表 Opus，采样率 48 kHz，双声道。

注意：payload type 不是 codec 的全球唯一编号，只在当前 RTP session 和协商上下文中有意义。

### 3.4 SSRC

SSRC（Synchronization Source）标识一个同步源。接收端用它区分不同 RTP 流。

常见情况：

- 一路音频一个 SSRC；
- 一路视频一个 SSRC；
- 多路编码层可能有多个 SSRC。

SSRC 是随机选择的 32 bit 值，不等同于用户 ID，也不应该被业务层当作稳定身份。

### 3.5 marker bit

marker bit 没有全局固定含义，由具体 payload format 定义。

常见用法：

- 视频：标记一帧的最后一个 RTP 包；
- 音频：某些 profile 中用于标记 talkspurt 的开始。

面试里要强调：不能脱离 payload format 解释 marker bit。

## 4. RTP、RTCP、UDP 的关系

RTP 最常运行在 UDP 上，因为实时媒体通常不能等待 TCP 的可靠重传。

```text
UDP 负责把数据报送出去
RTP 负责描述媒体包的顺序、时间、来源和负载类型
RTCP 负责反馈传输质量和同步信息
```

TCP 的问题是队头阻塞：如果前面的数据丢了，后面已经到达的数据也要等它补齐后才能交给应用层。这对实时音视频不友好。

但 RTP 并不是只能跑在 UDP 上。在一些受限网络环境下，也可能通过 TCP、TLS、TURN TCP 等路径承载，只是延迟和抖动风险更高。

## 5. RTCP 的作用

RTCP（RTP Control Protocol）和 RTP 配套使用。RTP 传媒体数据，RTCP 传控制和统计信息。

常见 RTCP 包：

- SR：Sender Report，发送者报告；
- RR：Receiver Report，接收者报告；
- SDES：Source Description，源描述，例如 CNAME；
- BYE：离开会话。

SR 的核心价值是把 RTP timestamp 映射到真实时间：

```text
RTP timestamp -> NTP time
```

这样接收端才能知道音频采样点和视频帧应该在什么真实时间播放，从而做音视频同步。

RR 通常反馈丢包、最高收到的 sequence number、interarrival jitter 等信息。发送端可以根据 RR 判断接收侧质量。

## 6. 抖动缓冲

RTP 接收端通常不会收到包就立即播放，而是先放入 jitter buffer。

jitter buffer 的作用：

- 等待轻微乱序的包；
- 平滑网络抖动；
- 按 RTP timestamp 恢复播放节奏；
- 判断过晚包并丢弃。

核心取舍：

```text
缓冲越大：抗抖动能力越强，但延迟越高
缓冲越小：延迟越低，但更容易卡顿、破音、花屏
```

## 7. 视频 RTP 基本规则

视频 RTP 有几个常见特点：

- 一帧通常远大于 MTU，需要拆成多个 RTP 包；
- 同一帧的多个 RTP 包通常 timestamp 相同；
- marker bit 常用于标记一帧的最后一个 RTP 包；
- 关键帧丢失影响很大；
- 一个 RTP 包丢失，可能导致整个视频帧不可解码。

以 30 fps 视频、90 kHz RTP clock 为例：

```text
每帧 timestamp 增量 = 90000 / 30 = 3000
```

如果收到：

```text
seq=100 ts=90000 M=0
seq=101 ts=90000 M=0
seq=102 ts=90000 M=1
seq=103 ts=93000 M=0
seq=104 ts=93000 M=1
```

可以理解为：

- `100-102` 属于同一视频帧；
- `102` 是该帧最后一个 RTP 包；
- `103-104` 属于下一帧。

### 7.1 实际 RTP 包长什么样

抓包里看到的 RTP 视频包，外层通常是：

```text
+-----------+------------+-------------+----------------------+
| IP header | UDP header | RTP header  | RTP payload          |
| 20 bytes  | 8 bytes    | >=12 bytes  | codec-specific data  |
+-----------+------------+-------------+----------------------+
```

RTP header 只描述这个媒体包的序号、时间戳、负载类型、SSRC 等信息。真正的视频数据在 RTP payload 里。

以 H.264 为例，如果一个 NALU 比较小，可以直接放进一个 RTP payload：

```text
+------------------ RTP packet ------------------+
| RTP header | H.264 NALU                         |
|            | +-----------+--------------------+ |
|            | | NAL hdr   | NAL payload        | |
|            | +-----------+--------------------+ |
+------------------------------------------------+
```

如果一个 H.264 NALU 太大，超过单个 RTP 包可承载大小，就会拆成多个 RTP 包。常见方式是 FU-A：

```text
原始 H.264 NALU:

+-----------+--------------------------------------+
| NAL hdr   | NAL payload                          |
+-----------+--------------------------------------+

拆成多个 RTP 包后:

+---------------- RTP packet 1 ----------------+
| RTP header | FU indicator | FU header | part1 |
| seq=100    |              | S=1,E=0   |       |
+----------------------------------------------+

+---------------- RTP packet 2 ----------------+
| RTP header | FU indicator | FU header | part2 |
| seq=101    |              | S=0,E=0   |       |
+----------------------------------------------+

+---------------- RTP packet 3 ----------------+
| RTP header | FU indicator | FU header | part3 |
| seq=102    |              | S=0,E=1   |       |
+----------------------------------------------+
```

这里要注意：

- `RTP header` 每个 RTP 包都有；
- `sequence number` 每个 RTP 包递增；
- 同一个视频帧拆出来的包通常 `timestamp` 相同；
- `M=1` 通常表示这一帧的最后一个 RTP 包；
- FU-A 里的 `S` 表示 NALU 分片开始，`E` 表示 NALU 分片结束；
- 接收端按 sequence number 收齐分片后，重组出原始 NALU，再交给 H.264 解码器。

## 8. 面试常见误区

### 8.1 RTP 等于 UDP

不对。UDP 是传输层，RTP 是应用层媒体传输格式。RTP 常跑在 UDP 上，但 RTP 的价值在于媒体时间、序列号、同步源和控制反馈。

### 8.2 RTP 保证实时

不对。RTP 只是提供实时媒体所需的信息。真正的低延迟还依赖网络路径、编码器、jitter buffer、拥塞控制、渲染管线等。

### 8.3 timestamp 是发送时间

不对。RTP timestamp 是媒体时间，不是 Unix 时间，也不一定等于发包时间。跨媒体同步通常需要 RTCP SR 把 RTP timestamp 映射到 NTP time。

### 8.4 payload type 全局固定

不对。现代 RTP 大量使用动态 PT。PT 的含义必须结合协商上下文理解。

### 8.5 RTCP 可有可无

不准确。简单单向播放也许可以没有 RTCP，但交互音视频通常依赖 RTCP 做质量反馈、同步和控制。

## 9. FAQ

### 9.1 文中提到的 MTU 是什么

MTU 是 Maximum Transmission Unit，最大传输单元，表示某一层网络链路上单个数据包一次能承载的最大大小。常见以太网 MTU 是 1500 bytes，这里的 1500 bytes 通常指 IP 包大小，不包含以太网帧头。

RTP 通常运行在 UDP/IP 上。如果以太网 MTU 是 1500，扣掉 IPv4 header 20 bytes、UDP header 8 bytes、RTP header 12 bytes，留给 RTP payload 的大约是：

```text
1500 - 20 - 8 - 12 = 1460 bytes
```

视频帧经常有几十 KB，明显大于 MTU，所以必须拆成多个 RTP 包发送。实践中通常会把单个 UDP/RTP 包控制在约 1200 到 1400 bytes 内，避免 IP 分片。

分片对实时音视频不友好：任意一个分片丢了，整个 UDP 包都无法恢复；有些 NAT、防火墙、运营商网络也会丢弃分片。

### 9.2 视频帧类型有哪些

视频编码里常见帧类型主要是 I 帧、P 帧、B 帧。它们是编码层概念，不是 RTP 协议本身的字段。RTP 只是承载编码后的数据。

| 帧类型 | 含义    | 依赖关系     | 特点                     |
| --- | ----- | -------- | ---------------------- |
| I 帧 | 帧内编码帧 | 不依赖其他视频帧 | 可独立解码，体积较大             |
| P 帧 | 前向预测帧 | 依赖之前的参考帧 | 体积较小，丢失会影响后续依赖它的帧      |
| B 帧 | 双向预测帧 | 依赖前后参考帧  | 压缩率更高，但会增加重排序延迟 (通常不用) |

H.264 里常见 IDR 帧。IDR 是一种特殊 I 帧，收到 IDR 后，解码器可以清空旧参考关系，后续帧不能再引用 IDR 之前的帧。

粗略关系：

```text
IDR 帧属于 I 帧
I 帧不一定都是 IDR 帧
关键帧通常指可作为解码恢复起点的帧
```

B 帧可能参考未来帧，所以显示顺序和编码顺序可能不同。低延迟通话、WebRTC 场景中通常会尽量少用或不用 B 帧。

## 10. 一句话总结

RTP 的本质是：在不追求传输层可靠性的前提下，把实时媒体播放和质量控制所需的最小元数据放进每个媒体包，并用 RTCP 补充跨包、跨流、跨端的控制信息。

面试回答可以压缩成：

```text
RTP 通常跑在 UDP 上。
sequence number 用来判断包顺序和丢包。
timestamp 用来恢复媒体播放时间，不是发送时间。
SSRC 用来标识一条媒体源。
payload type 用来说明负载格式，但动态 PT 要结合协商结果理解。
RTCP 用来做质量反馈和音视频同步。
```
